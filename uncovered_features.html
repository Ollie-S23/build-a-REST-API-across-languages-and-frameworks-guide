23a. What this guide leaves out

A guide that tried to cover everything would never be finished. These are the topics that real APIs often need but that are not built or tested here. Each has a short explanation and links to documentation. Some of them might be covered in a future version of this guide, but nothing below is promised, and none of the code in steps 0 to 22 depends on them.

MoreCursor ("keyset") pagination
The limit and offset used here get slower as the offset grows and can skip or repeat rows if data changes while someone pages. Cursor pagination says "give me the 20 rows after the one with this id and sort key", which stays fast and stable on large tables.
  • Use The Index, Luke: Paging through results
MoreAPI versioning and breaking changes
Once other people call your API you cannot rename a field freely. Common answers: a version in the path (/v1/contacts), a version in a header, or only ever adding fields and never removing them. Decide a deprecation process before the first breaking change, not after.
  • Google API design guide: Versioning
  • Stripe: API versioning
MoreIdempotency keys
A client that loses its connection after POST does not know whether the contact was created, and retrying could create it twice. An idempotency key is a unique value the client sends with the request; the server remembers the reply for that key and returns it again instead of repeating the work. Step 17 made linking a tag idempotent by design; creating things needs the key.
  • IETF draft: The Idempotency-Key HTTP header
  • Stripe: Idempotent requests
MoreBackground jobs and message queues
Work that is slow or can fail (sending many emails, resizing images, calling other services) should not run inside the request. A job queue (Redis-backed queues, RabbitMQ, a cloud queue) holds the work and separate worker processes do it, with retries. Steps 15 and the webhooks chapter send in the background inside the server, which is fine for small amounts and is lost on a crash.
  • RabbitMQ: Tutorials
  • Redis: Queue patterns
MoreFull-text search
The name filter here is "contains". Real search needs word splitting, ranking, typo tolerance and stemming. PostgreSQL has built-in full-text search; larger systems use a search engine such as OpenSearch, Elasticsearch, Meilisearch or Typesense, kept in sync with the database.
  • PostgreSQL: Full text search
  • SQLite: FTS5
MoreLogin with other providers, and two-factor sign-in
Step 8 and 15 store passwords. Many apps instead use "Sign in with Google" or similar (OAuth 2.0 and OpenID Connect), or add a second factor (an authenticator app code or a passkey). Both are easy to get subtly wrong, so use a maintained library or a hosted identity service rather than writing them.
  • OAuth 2.0 Simplified
  • OpenID Connect
  • WebAuthn guide
MoreSeveral customers in one API (multi-tenancy)
When different companies use the same deployment, every table needs a tenant id, and every query must filter by it, or one customer sees another's data. Choices: a tenant column on every row, a schema per tenant, or a database per tenant, trading isolation against cost. PostgreSQL row-level security can enforce the filter in the database itself.
  • PostgreSQL: Row security policies
MoreSoft deletes, history and "undo"
Instead of removing a row, set a deleted_at time and hide such rows from every query. It allows restore and keeps references valid, at the cost of every query remembering the filter and of rows that must still be removed eventually (for example when a person asks for their data to be erased). Step 14's audit log records who did what, but not the old values.
  • PostgreSQL: Row-level security (to hide deleted rows)
MoreImporting and exporting data (CSV)
Bulk import has its own problems: a half-finished import, duplicates, bad rows, and a long request. Usually it is an upload that creates a background job and reports progress and a list of rejected rows. Export should stream the rows rather than build the whole file in memory.
  • RFC 4180: CSV
MoreTracing a request across services (OpenTelemetry)
Step 13 gave every request an id and the metrics chapter counts requests. When a request passes through several services, distributed tracing links the pieces into one timeline. OpenTelemetry is the common standard for traces, metrics and logs and works in every language used here.
  • OpenTelemetry documentation
  • Prometheus: Getting started
MoreGraphQL and gRPC
This guide builds a REST API: many URLs, one verb each. GraphQL offers one URL where the caller describes exactly the fields and related objects it wants (useful when screens need data from many tables at once). gRPC uses a binary format and a contract file, and suits calls between your own servers more than browsers.
  • GraphQL: Learn
  • gRPC: Introduction
MoreLoad testing and contract testing
The tests used here check correctness. Load tests (k6, Locust, wrk) find how many requests per second the server survives and where it breaks, and are needed before you promise any capacity. Contract tests check that your replies still match the published openapi.json, so a change cannot silently break a client.
  • k6 documentation
  • Schemathesis (tests from an OpenAPI file)
MoreHTTPS, certificates, backups and continuous delivery
Step 16 shows Docker, but running for real also needs HTTPS (usually terminated by a reverse proxy or the host, with certificates renewed automatically), tested backups and a restore you have actually practised, secrets stored outside the code, and an automatic build-test-deploy pipeline. None of these were tested for this guide.
  • Let's Encrypt: Getting started
  • PostgreSQL: Backup and restore
  • GitHub Actions documentation
  • The Twelve-Factor App
