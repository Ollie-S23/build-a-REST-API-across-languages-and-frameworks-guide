Phase 21 ? File handling

File uploads (avatars, attachments) Optional feature

Goal. Accept files safely and store them outside the API when possible.

21a. Send the file with an HTTP request

Use POST to accept an uploaded file. For HTML forms or a request that contains both fields and binary data, use multipart/form-data; do not use URL-encoded form data for binary files. The request body contains separate parts separated by a boundary, and each part may provide a field name and, for a file, a filename. A framework should decode and validate those parts before touching the filesystem.

MoreRequest and multipart details

The browser or client sends Content-Type: multipart/form-data; boundary=.... The boundary is a random delimiter, and every part can be read by a framework without you parsing the raw body yourself. Include a size limit before full in-memory parsing, and reject requests that exceed it rather than collecting the whole upload.

  • MDN: POST and multipart/form-data

21b. Validate the upload in depth

Use a business-driven allowlist of file types instead of accepting every extension. Validate the real content and file signature as well as the name and declared Content-Type; the declared MIME type is sent by the client and is easy to spoof. Check double extensions, null bytes, case variants, alternative executable extensions, alternate data streams, filename length and unsafe characters. Where it adds enough protection, scan for malware or reconstruct document content; keep processing libraries and sandboxes up to date.

MoreContent and filename checks
  • Decode the filename first, then validate it. Decode only in your framework's normal file parser rather than manually stripping encoded text.
  • Do not trust an extension alone or trust Content-Type alone. Compare the signature or decoded content with the expected type.
  • Generate the stored filename on the server, preferably a random UUID or GUID. If a user filename is required, limit its length and characters and reject leading periods or traversal sequences.
  • Do not use uploaded PDF, HTML, SVG or document content as active code on a same-origin page. Re-encode images where appropriate and avoid unnecessary image metadata.
  • ZIP files and complex office formats have a large attack surface; reject them unless the business truly needs them.
  • OWASP: File Upload Cheat Sheet

21c. Store and retrieve files safely

Only let authorized users upload. Put files in object storage or outside the web root, not next to executable application files. If public retrieval is needed, map an opaque application id to the stored object rather than exposing the original filename or arbitrary filesystem paths. Set a size and storage quota, protect the upload route against CSRF, remove stale or disallowed objects, and log upload and deletion attempts without storing sensitive file contents in application logs.

MoreStorage and retrieval checklist
  • Prefer private object storage with signed or short-lived download URLs for private files.
  • Use a random server-side key and keep the original name only as metadata if the UI needs it.
  • Use a separate origin or safe content-disposition policy for public uploads so uploaded content cannot act as part of the API or web application.
  • Scan, review or sandbox high-risk file types when resources allow, and provide an abuse or illegal-content reporting process.
  • Back up object storage according to retention rules and delete both the object and database reference when the file is deleted.
MoreFile upload references
  • MDN: POST and multipart/form-data
  • OWASP: File Upload Cheat Sheet

21d. What the API should expose

Keep the upload contract separate from the contact route until the upload is actually attached to an account or contact. This avoids a file existing with no owner and gives the client a two-step flow: create or replace the upload, then save its opaque id on the contact or account.

RequestExpected result
POST /uploads with multipart/form-data201, an opaque id, sanitized metadata and a short-lived download URL. 413 for too large, 415 for a rejected type, 403 for an unauthorized caller.
GET /uploads/{id}302 to a signed private URL, or 200 from a dedicated public file origin. 404 for another account's private file.
DELETE /uploads/{id}204 if deleted or already absent. Remove the object and database metadata, revoke future download URLs and record the deletion.
PATCH /contacts/{id} with avatar_upload_id422 if the upload does not exist or is owned by another account; otherwise replace only the avatar reference.

21e. The shared upload checks

Compared with an endpoint that reads text fields, an upload endpoint first checks the request boundary and size, then uses framework parsers to obtain the file stream. It never joins the client filename to a storage directory. The small example below is framework-independent; production code should use the framework's streaming parser and object-storage SDK.

Do not trust filename, Content-Type or file size sent by the client. Always combine server limits, a real-content check, a generated stored name and authorization. A single validation technique is not enough.

21f. Database metadata and deletion

Store only metadata and the object key in the database. The object key is opaque and unrelated to the user filename. Deleting the avatar may mean updating the contact and deleting the object; make each operation idempotent and verify ownership before changing either one.

21g. Tests and failure modes

CheckExpected result
PNG signature with a renamed .php filename415; the intended allowlist rejects the executable extension.
PNG signature with 2 MiB plus one byte413; no object or database row is created.

Private file URL is opened after deletion or ownership changesDenied; do not assume signed URLs remain valid forever.
If it failsTypical upload failures
  • 413 despite a small file: a proxy or framework limit is lower than the application limit.
  • 415 for valid images: inspect the signature and allowlist; do not compare only the browser MIME type.
  • 400 on a boundary: confirm the client sets the complete multipart boundary header.
  • Timeout or memory spike: stream to disk or object storage with a limit instead of read() into memory.
  • File is public unexpectedly: serve it from a different origin or add authorization in the download route.
MoreGo further
  • Generate thumbnails asynchronously and keep the original private.
  • Rebuild or re-encode images in an isolated worker with strict resource limits.
  • Use antivirus or document sanitization for business-critical untrusted files.
  • Add resumable uploads and an explicit confirmed/failed processing state.
  • Encrypt private objects at rest and use short-lived download credentials.

Phase 22 ? Personal data

Personal data and privacy law Optional feature

Goal. Understand the privacy obligations that may apply to personal data.

22a. Decide whether the data is personal

Contacts are personal data where they identify or can be linked to a person. That includes names, email addresses, phone numbers, account identifiers, uploaded avatars and company or company-employee relationships. Different laws may apply based on the user's location and the organization's place of business. Do not treat these rules as optional just because the API is small.

22b. Record a lawful, documented purpose

Before collecting or using a field, define the reason, who receives it, how long it is kept and how an individual can exercise their rights. Only collect fields needed for the stated purpose, and apply strict access control. Under GDPR principles, an organization should provide clear information about processing, be able to demonstrate compliance and address subject-rights requests such as access and erasure. The exact right, exception and deadline can vary by jurisdiction.

MoreGDPR planning checklist
  • Document what is collected and why, and keep the privacy notice accurate.
  • Minimize fields, set retention periods and delete or anonymize data when the purpose ends.
  • Support data export and an erasure workflow; exceptions may require retaining evidence or security records.
  • Use appropriate security and access controls, and keep a process for data breaches.
  • Use a qualified privacy or legal adviser for legal determinations and for a real-world GDPR compliance program.
  • GDPR.eu: GDPR overview, compliance, and templates

22c. Apply the Australian Privacy Principles where relevant

The Australian Privacy Principles are the centerpiece of the privacy framework in the Privacy Act 1988 for covered organizations and agencies. Its 13 principles govern collection, use and disclosure, governance and accountability, integrity and correction of personal information, and individual access. They are principles-based and technology-neutral, but a breach can be interference with privacy and lead to regulatory action or penalties.

MoreAustralian privacy checklist
  • Use a privacy notice and appropriate collection and consent practices for the real circumstances.
  • Explain and control secondary use or disclosure; limit it to purposes covered by notice or applicable consent and law.
  • Give people a way to access and correct their personal information.
  • Keep reasonable governance, integrity, security and accountability measures.
  • Maintain a Notifiable Data Breach assessment process and consult the OAIC guidance when an eligible data breach may have occurred.
  • OAIC: Australian Privacy Principles
  • OAIC: Applying the principles
  • OAIC: Principles quick reference

22d. Build user rights into the API

Plan export, access, correction and deletion paths before they become support requests. An export should contain only information the requester is allowed to receive, not another user's private data. Deletion should remove or anonymize personal data while preserving records needed for an allowed exception, accounting or security purpose. Audit administrative and deletion actions, and verify that third-party stores, backups and object storage follow the same lifecycle rules.

MorePrivacy and file interaction

An uploaded avatar or document can contain personal data even if the database stores only a link. Apply the same access, export, deletion and retention rules to the object, metadata and database record. When a private file is erased, also revoke existing download URLs and remove it from caches or temporary processing locations where appropriate.

MorePrivacy law references
  • GDPR.eu: Official text overview and compliance resources
  • OAIC: Australian Privacy Principles

22e. The privacy lifecycle in the API

A privacy-safe API separates "store personal data", "prove why it is stored", "return it to its owner", "correct it" and "delete or anonymize it". A data field should have an owner, purpose, collection time, source and retention rule in code or a documented data register. The example below is deliberately small, but a real system should synchronize database records, object storage, caches and third-party processors.

Request or operationRequired behavior
GET /privacy/exportReturn only the authenticated account's data. Generate the archive asynchronously if it may be large. Record the request and its completion.
GET /privacy/fieldsOptionally describe the fields, purpose and retention period shown in a privacy notice. Do not invent an end-user consent or legal-right result.
PATCH /contacts/{id}Use normal authorization, but write an audit entry for correction of personal data. Include who changed what, without logging the old secret or full document.
POST /privacy/erasureStart an authorized erasure request. Return a request id and never let deletion occur without an ownership or administrator check.
POST /privacy/breachA restricted internal operation for security staff to record affected records, discovery time, scope and the required assessment.

22f. Record purpose and retention

For SQL databases, a privacy register can be documentation only; a production system should also put policy fields next to sensitive records or in a controlled policy table. The migration below gives every contact a purpose, collection date and review date. The application may derive a default retention date, but legal exceptions and jurisdiction-specific rules must come from reviewed policy data, not an arbitrary API constant.

Do not export secrets, password hashes or another account's private fields. An export is a copy of personal data; it is not an administrator escape hatch. Apply field-level authorization to nested contacts, notes and uploads.

22g. Implement erasure safely

Erasure is usually a workflow, not one database statement. First authorize and verify the request, then remove or anonymize records across every system, revoke signed URLs and delete object storage files. Keep only the minimum evidence needed for security or a lawful exception, and do not silently claim a result when an asynchronous worker or backup remains.

22h. Backup and breach implications

A privacy request should not stop at the live database. Search application logs, exports, caches, analytics, email queues, backup retention, and third-party processors. A backup may need a separate lifecycle or an encrypted erasure marker until restore. Do not put full personal records or file contents in logs or analytics events.

WhyWhy not delete every row immediately?
Legal exceptions, account disputes, fraud prevention and security investigations may require limited evidence to be retained. The application should return only the minimum, restrict access to it and document the reason and expiry. A qualified adviser and the actual jurisdiction determine the final rule.

22i. Tests and failure modes

CheckExpected result
User asks for another account's export403 or a non-disclosing 404; no private fields are returned.
User deletes or exports their avatarExport includes only authorized metadata or bytes; erasure removes the object reference and object.
Erasure succeeds for SQL but object deletion failsKeep the job pending and retry; do not report complete.
Retention date passesRun a reviewed retention job; preserve exceptions and document each anonymization or deletion.
Privacy field is added to a contactThe data-register entry, export, correction, audit and deletion paths include it before release.
Suspected personal-data breachRestrict access, preserve evidence, assess affected people and assess whether regulatory reporting is required.
If it failsPrivacy workflow failures
  • Export is missing uploaded files: include object metadata and serve approved bytes through the same authorization rules.
  • Deletion leaves a cache or URL valid: invalidate sessions and cache entries and revoke signed download credentials.
  • Audit log contains names or file contents: reduce it to actor, action, record id and field names; store sensitive values separately only when legally required.
  • A backup is blocking erasure: state the retention period in the workflow and apply a restore-time deletion process rather than falsely claiming the backup is rewritten.
  • A jurisdiction is unknown: stop and ask the organization for a qualified legal determination instead of assuming one law applies to everyone.
MoreGo further
  • Build a machine-readable data catalog and connect it to export and deletion jobs.
  • Add consent and purpose records only where the applicable law requires them.
  • Add field-level encryption and key rotation for highly sensitive fields.
  • Run scheduled retention jobs with preview, exception and operator-review modes.
  • For a breach, follow a tested incident-response plan and the reporting guidance for each affected jurisdiction.
